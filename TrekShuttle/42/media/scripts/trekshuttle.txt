    /*  The phaser.

        An ordinary build 42 sidearm in every respect except that TREK_Phaser
        .lua keeps it charged, unjammed and undamaged, which is what makes it
        a phaser rather than a pistol.

        AmmoType is base:bullets_9mm and that is deliberate, not laziness.
        AmmoTypes are registered in Java through AmmoType.registerBase and
        there is no script syntax anywhere in build 42 for a mod to add one --
        `bullets_9mm` appears in media/scripts only ever as the *value* of an
        AmmoType line, never as a definition. A made-up id resolves to nothing
        and the weapon will not fire, silently. Since the charge is restored
        far faster than it can be spent, no 9mm is ever drawn from the
        player's own stock; the ammunition type is a formality the engine
        insists on.

        MaxAmmo is high for the same reason: the top-up runs on a slow tick,
        and a deep charge means even a burst fired between two ticks cannot
        empty it.

        WeaponSprite names a vanilla in-hand model, because a pistol shape the
        game already has is not worth rebuilding.

        This comment used to claim a custom one "needs a rigged attachment set
        rather than a static mesh". That is wrong, and it was wrong in a way
        that quietly ruled out every melee weapon on the roadmap. A weapon
        model is a plain static mesh -- no bones, no skinning, no animation
        files. `WeaponSprite` names a `model` block exactly as StaticModel
        does; the block takes a mesh and a texture; the swing comes from
        `SwingAnim`, which is a name resolved against the game's own global
        animation set. Vanilla's own Katana model block is four lines and two
        attachments, and a Workshop mod ships custom in-hand blades as `.x`
        files whose only frames are `Root` and a transform.

        The two attachments are `Bip01_Prop2` (where it sits in the hand) and
        `world` (how it lies when dropped), and both are optional -- omit them
        and the engine falls back to a default placement. Where a blade hangs
        when slung is not on the weapon model at all: the item's
        `AttachmentType` is routed through ISHotbarAttachDefinition.lua and
        AttachedLocations.lua to an attachment on the *character* model.  */

    /*  ------------------------------------------------------------------
        The galley's drinks.

        A build 42 drink is not a food item. It is a *fluid* -- which carries
        every effect, the colour and the name -- held in a vessel item that
        owns a FluidContainer component. Drinking reads the fluid, so the
        item blocks below have no ThirstChange of their own and should not
        grow one: it would be ignored, which is the silent-failure shape this
        mod keeps being bitten by.

        Three things about this were verified against the engine rather than
        assumed, because each would have failed quietly:

        1. A mod may declare `fluid` blocks in its own media/scripts. The
           vanilla ones all live under scripts/generated/, which made it look
           like a generated-only format; FluidDefinitionScript tracks isVanilla
           and modId, FluidType has a `Modded` constant for exactly this, and
           at least one Workshop mod ships fluids from its own scripts folder.
        2. A modded fluid is *not* reachable as FluidType.<name>. FluidType is
           a fixed Java enum and every modded fluid is FluidType.Modded; the
           name is a string. From Lua the handle is Fluid.Get("<name>"), and
           FluidContainer:addFluid has (String, float), (FluidType, float) and
           (Fluid, float) overloads -- vanilla Lua uses all three.
        3. ColorReference takes a registered colour name, not a hex value, and
           an unknown one is **fatal**. This comment used to say it "logs
           Cannot find color: rather than drawing black, so a typo is visible".
           It does not log and carry on: FluidDefinitionScript.getColor throws
           RuntimeException("Cannot find color: X"), that aborts
           ScriptManager.loadScripts, and the world then refuses to load at all
           with "there are script load errors". `ClearBlue` cost exactly that.

           The colours below are ones vanilla's own fluids use, which is the
           only list proven to resolve. Reading names out of Colors.class is
           what produced `ClearBlue` in the first place -- a string being
           present in a class file is not the same as it being a registered
           name, which is "the jar is not the API" one level down.
           tests/test_assets.py checks against the vanilla set now.

        InitialPercentMin/Max fill the vessel when the item is created, so a
        bottle found in the galley is a full bottle.

        No IconFluidMask, deliberately. A mask is a second texture the fluid's
        colour is painted through, so one empty-vessel icon can show any drink
        at any level. It is optional -- 61 of vanilla's 133 fluid containers
        ship without one, Kettle and Bleach among them -- and exactly how it
        composites has not been seen in this game yet, only reasoned about. An
        icon drawn empty plus a mask that turns out not to work the way it was
        reasoned about is a drink that looks empty in the inventory and
        reports nothing: the "present, drawn and inert" shape this mod has
        already paid for five times. So the liquid is painted into the icon
        instead, which is right whether or not a mask would have worked, and
        the mask is a polish pass for after somebody has watched one render.
        ------------------------------------------------------------------ */

        ever holds one, no locker stocks it, and it has no icon because it is
        never drawn: it exists only so a HandWeapon can be handed to
        IsoTrap.new().

        That constructor is why. It copies the whole explosion off the weapon
        -- getSensorRange, getFireRange, getFireStartingEnergy,
        getFireStartingChance, getExplosionPower, getExplosionRange,
        getSmokeRange, getNoiseRange, getExtraDamage and the rest -- so a nil
        weapon is a NullPointerException on the first of them, which is exactly
        how the first build failed in game:

            NullPointerException: Cannot invoke "HandWeapon.getSensorRange()"
            because "weapon" is null

        The numbers mirror vanilla's PipeBomb because a torpedo is a pipe
        bomb's blast delivered from the air, and borrowing them means the
        damage is already balanced against everything else that explodes here.

        about the engine and false about the weapon: IsoTrap.drawCircleExplosion

        visible part of an explosion. At 0 the torpedo killed what was in the
        blast and nothing was ever seen to happen, for three commits, while
        every check passed.

        Vanilla's PipeBomb does ship 0 -- because a pipe bomb is not meant to
        be arson. A photon torpedo is. See PHOTON_TORPEDOS.md, and
        DEV_GUIDE.md's "A guard is only as good as the goal it was written
        from".
